    What this prototype demonstrates
    
    
    
      
    Evaluation areaDemonstrated by
    
      
    Understanding of the problemBoth submitter paths render from one definition. Switch the
        submitter type on the reporting form and watch fields, wording, and required-status change.
    
      
    Soundness and feasibilityA working rules engine, not a mock-up. The trace panel shows each
        condition and its evaluated result in real time.
    
      
    Innovation and originalityThe Admin Console edits the same definition the form reads.
        Change a label, help text, required flag, or branching condition and it applies immediately in
        English and Spanish with no deployment.
    
      
    Technical risk mitigationAssistance is deterministic. Leave the AI toggle off and every
        validation and guidance requirement is still met — the fallback is the primary mechanism.
    
      
    PRS#1 — branching correctnessSelect Healthcare provider, then Vaccination error with no
        adverse event. The entire adverse-event section is suppressed and the structured output records the
        suppression explicitly.
    
      
    PRS#2 — responsive designMobile-first layout; resize to below 960px to see the single-column
        reflow. No horizontal scrolling at 320px.
    
      
    PRS#14 — accessibilityOperable by keyboard alone. Semantic landmarks, fieldset and legend
        grouping, programmatic label association, aria-describedby help text, aria-invalid on errors, and a
        focus-managed error summary.
    
      
    PRS#19 — English and Spanish parityBoth languages render from the same definition, so a
        field cannot exist in one language and not the other. That class of localization defect is designed out.
    
      
    Scalability and extensibilityPhase 2 image upload is a configuration toggle in the Admin
        Console, not a redesign.
    
    
    
  
    
  
    
    
    Accessibility implementation notes
    
    
      
      
    • Skip-to-content link as the first focusable element.
      • 
      
    • Tab list implements the ARIA tabs pattern with arrow-key navigation and roving tabindex.
      • 
      
    • Every control has a programmatically associated label; help text is linked via aria-describedby.
      • 
      
    • Radio and checkbox groups use fieldset and legend, so a screen reader announces group context.
      • 
      
    • Validation errors set aria-invalid, are announced through a role="alert" summary, and each entry links to its field.
      • 
      
    • The rules trace and assistance regions use aria-live="polite" so changes are announced without stealing focus.
      • 
      
    • Visible focus indicator at 3px with offset; colour is never the sole carrier of meaning.
      • 
      
    • Body text meets 4.5:1 contrast; the interface is fully operable at 200% zoom.
      • 
    
    
    
    Scope of this prototype. This is a front-end demonstration of the
      architecture. It has no backend, no database, and no VAERS integration, and it stores nothing. Automated
      WCAG scanning and manual assistive-technology testing with JAWS, ZoomText, and Dragon NaturallySpeaking
      are performed against the delivered application under PWS 3.5, not against this demonstration.
